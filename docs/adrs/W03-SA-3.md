# ADR W03-SA-3 — KG/Context-graph representation for production

**Status:** Accepted · **Date:** 2026-06-11 · **Scenario:** W03-SA-3
**Deciders:** acquire-gov pair · **Live defense:** Fri W4 (19 Jun 2026)

---

## Decision

Use **Postgres recursive CTEs (`WITH RECURSIVE`) over the existing acquire-gov Postgres** as the production knowledge/context-graph representation. Do **not** add Neo4j as a third datastore, and do **not** treat NetworkX in-process as production-viable beyond single-tenant scale.

The deciding factor is not raw traversal capability — Neo4j is the stronger engine in the abstract — but the intersection of the four constraints. At the stated data volumes (~17 entity types; ~100 vendors / ~500 proposals / ~80 active contracts per tenant) the graph is *small*, and Postgres recursive queries comfortably serve 4–6 hop traversals such as "every contract this vendor won with red CPARs" within the <200ms p95 budget, while keeping the FedRAMP boundary, backup story, and on-call rotation unchanged.

---

## Context

Four constraints drive this decision:

1. **Latency budget.** CO graph-traversal queries must run **<200ms p95** against the 17-entity KG (Vendor ↔ Proposal ↔ Evaluation ↔ Award ↔ ContractModification ↔ Cpar).
2. **Multi-tenant boundary.** `agency_id` isolation must be enforced on every query (Item 10), with audit-log integration (Item 2).
3. **FedRAMP posture.** The authorization boundary must stay intact; every new control surface is expensive.
4. **Ops budget.** Constrained — a third datastore adds backup, monitoring, and on-call cost the engagement cannot absorb.

The existing stack is **Postgres + MongoDB Atlas**. Recursive CTEs are standard SQL, supported in PostgreSQL since 8.4 (2009) and current through 18.x; the documentation explicitly frames them for "hierarchical or tree-structured data" and graph traversal, with built-in `SEARCH` ordering and `CYCLE` detection clauses [1]. Neo4j's Cypher offers purpose-built variable-length and quantified path patterns for the same traversals [2]. NetworkX provides in-process traversal with well-documented complexity (BFS `O(V+E)`, Dijkstra `O((V+E) log V)`) but is a library loaded per process, not a persistent multi-tenant datastore [3].

A material finding: as of the Neo4j Trust Center snapshot dated 2026-06-02, Neo4j's published compliance set includes SOC 2 Type 2, SOC 3, ISO/IEC 27001:2022, CSA STAR Level 1, HIPAA, GDPR, and CCPA — but **FedRAMP is not listed** [4]. Neo4j Aura therefore cannot be dropped into the FedRAMP boundary as an authorized service; a Neo4j path would require self-hosting inside the existing boundary, adding controls rather than inheriting them.

| **Cost shape** (12-mo engagement) | 5 — zero added license or infra; reuses existing Postgres | 2 — separate license + Aura cloud or self-hosted ops time | 4 — zero added infra; Python process memory + reload overhead |
| **Operational burden** — backup, monitoring, on-call, FedRAMP control delta | 5 — no new datastore; existing backup/monitoring/on-call unchanged | 2 — "third-datastore tax": new backup, monitoring, on-call, and ~6–12 added FedRAMP controls | 4 — no datastore, but app-tier memory/process management and rebuild-on-deploy |
| **Security posture** — `agency_id` boundary, audit log, FedRAMP | 5 — `WHERE agency_id = $1` inside the existing boundary and audit pipeline | 2 — Aura **not** FedRAMP-listed [4]; self-host required; `agency_id` constraint needed on *every* match (easy to omit) | 3 — pre-filter at graph-load time only; audit integration must be built; in-app, so inside existing boundary |
| **Maturity** | 5 — SQL-standard, stable since PostgreSQL 8.4 (2009), current 18.x [1] | 5 — very stable, mature engine, frequent Cypher releases [2] | 4 — stable library (3.6.x, 2025) but not a production datastore [3] |
| **Exit cost** — switch backend in 24 months | 3 — porting recursive SQL → Cypher later is significant, but no lock-in beyond SQL | 2 — Cypher → SQL port plus data migration | 5 — trivial; was never persistent |
| **Total** | **27** | **18** | **23** |

## Consequences

**What we give up by choosing Postgres recursive CTE.** Query-authoring complexity. Writing a correct 6-hop traversal with cycle detection in recursive SQL is genuinely harder than the equivalent Cypher pattern; the cohort must be trained in the `WITH RECURSIVE` + `CYCLE`/`SEARCH` idiom [1], and reviewers must verify `agency_id = $1` appears in both the anchor and recursive terms. We also accept a moderate future exit cost if traversal needs ever outgrow Postgres.

**What rejecting Neo4j costs us.** We forgo the most ergonomic and highest-performing traversal engine. If query patterns later become deep (>8 hops), high-fan-out, or analytically graph-heavy (centrality, community detection), revisit — but only via self-hosting inside the FedRAMP boundary, since Aura is not FedRAMP-authorized as published [4].

**What rejecting NetworkX costs us.** Almost nothing for production; its trivial exit cost makes it a fine *prototyping* tool. The scale ceiling is the disqualifier: per-query load latency scales with graph size, so it may pass at one tenant and break across ~50 agencies. It is not multi-tenant production infrastructure.
