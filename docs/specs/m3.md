# M3 — Agentic Modification + Invoice Workflow (Implementation Spec)

**Source ADR + PRD:** [ADR-0006 — Contract-Lookup SF-30 Modification Workflow](../adrs/0006-contract-lookup-sf30-workflow.md) · [PRD §6 M3 (REQ-AGT-1/2/6)](../prd/phase-1-ai-adoption.md)
**Status:** Draft
**Date:** 2026-06-11
**Service:** `services/ai-orchestrator` (Python / FastAPI / LangGraph)

---

## Purpose

This spec breaks the PRD's **M3 multi-agent flow** (REQ-AGT-1/2/6) and ADR-0006 into buildable phases. The PRD says **what** to build and **why**; this document says **in what order** and shows **small, clear code** for each step. Every snippet is meant to be clear — one idea per function.

M3 has **two layers**:

1. **The multi-agent triage flow** (Phase 7) — the **outer** graph. Every inbound item (a modification request **or** an invoice) passes through an **anomaly-detector → adjudicator → decision-router**, and the router sorts it into one of three lanes: **auto-process**, **HITL-escalate**, or **return/route** (REQ-AGT-1/2). Auto-processing is **default-deny** and bounded by an explicit, testable policy (REQ-AGT-6).
2. **The SF-30 modification workflow** (Phases 0–6) — the **inner** graph (ADR-0006). When a modification request lands in the HITL lane, this is the processing path: look the contract up, auto-fill the static SF-30 blocks, classify, draft the rationale through the ADR-0005 grounded pipeline, and route through a hard CO approval gate before submission. No document upload, no PyMuPDF.

> **Build order is bottom-up; runtime is top-down.** Phases 0–6 build the inner SF-30 workflow first; Phase 7 wraps it with the triage flow. At runtime the triage flow runs first and *invokes* the SF-30 workflow as a compiled subgraph (Step 7.5).

### The graphs we are building

The outer triage flow (Phase 7):
```
ingest → anomaly_detector → adjudicator → decision_router
                                            ├── auto_process    (reversible ∧ delegated ∧ under-threshold ∧ anomaly-free)
                                            ├── hitl_escalate   (reserved ∨ irreversible ∨ over-threshold ∨ flagged) → SF-30 workflow
                                            └── return_route    (improper invoice, more-info, COR↔CO, hold)
```

The inner SF-30 workflow (Phases 0–6), invoked as the HITL processing subgraph:
```
lookup → validate → populate → classify → derive_consent → retrieve → confidence
  → draft → faithfulness → assemble → CO GATE → (consent?) → submit
```

Each box becomes one LangGraph **node**. The library and versions are already pinned (`langgraph==1.2.4`, `langchain==1.3.4` in `services/ai-orchestrator/requirements.txt`) — no new top-level dependency except the MongoDB checkpointer (Phase 4).

## Phase 0 — Scaffolding: state + empty graph

**Goal:** Define the shared state object and wire an empty graph that runs end-to-end with placeholder nodes. Nothing real happens yet — we prove the wiring.

### Step 0.1 — Define the workflow state

LangGraph passes one **state** dict between every node. We declare its shape with `TypedDict` (the official LangGraph pattern). Fields come straight from ADR-0006 §"State Schema Additions".

`app/workflow/state.py`
```python
from typing_extensions import TypedDict


class WorkflowState(TypedDict):
    # --- CO input ---
    contract_number: str          # base contract the CO entered, e.g. "GS-35F-0001V"
    change_request: dict          # CO-stated change: funding delta, PoP, scope

    # --- filled by the workflow ---
    contract_record: dict         # the looked-up record + source-of-record citation
    populated_fields: dict        # SF-30 block -> {value, source_citation}
    form_draft_id: str            # the draft ContractModification being written

    # --- classification (Block 13) + provenance ---
    block13_classification: dict  # 13A-13E path, modType, FAR basis, retrieved
                                  # clause ids, model+version, confidence — shown
                                  # at the CO gate so the CO can verify the call

    # --- integrity ---
    package_hash: str             # immutable hash of the material package; CO
                                  # approval, consent, and execution all bind to
                                  # this exact version (a material edit changes it)

    # --- gate + decision ---
    gate_status: str              # e.g. "CONTRACT_NOT_FOUND_AWAITING_CO_REVIEW"
    co_decision: str              # "pending" | "approved" | "denied" (review gate)
    modification_bilateral: bool  # FAR 43.103(a) bilateral vs (b) unilateral —
                                  # DERIVED server-side from modType, never the LLM
    contractor_consent: str       # "not_required" | "pending" | "recorded"
    co_execution: str             # "pending" | "executed" | "aborted" — the
                                  # distinct final-package execution decision
                                  # (FAR 43.102), separate from co_decision
```

> `co_decision` (approve the *package to proceed*) and `co_execution` (execute the
> *final, signed* package) are two separate CO acts — see Phase 5. `modification_bilateral`
> and `contractorConsentRequired` are **not** LLM outputs; they are derived deterministically
> from the classified `modType` (Step 2.1b) and re-validated on the write path.

> Official `TypedDict` state shape — see [Graph API overview](https://docs.langchain.com/oss/python/langgraph/graph-api).

### Step 0.2 — Build the graph skeleton

We add the nodes and the fixed edges. The order is a **hard rule** (ADR-0006 §"Workflow State Order"), so we use plain `add_edge` for the straight-line steps.

`app/workflow/graph.py`
```python
from langgraph.graph import StateGraph, START, END

from app.workflow.state import WorkflowState
from app.workflow import nodes


def build_graph() -> StateGraph:
    builder = StateGraph(WorkflowState)

    # register each node (functions live in nodes.py)
    builder.add_node("lookup", nodes.lookup_node)
    builder.add_node("validate", nodes.validate_lookup_node)
    builder.add_node("populate", nodes.populate_fields_node)
    builder.add_node("classify", nodes.classify_modification_node)

    # the straight-line edges (order cannot change)
    builder.add_edge(START, "lookup")
    builder.add_edge("lookup", "validate")
    builder.add_edge("validate", "populate")
    builder.add_edge("populate", "classify")
    builder.add_edge("classify", END)   # END moves to the next phase later

    return builder
```

> Official `StateGraph` / `add_node` / `add_edge` / `START` / `END` pattern — see [Graph API overview](https://docs.langchain.com/oss/python/langgraph/graph-api) and the [StateGraph reference](https://reference.langchain.com/python/langgraph/graph/state/StateGraph).

**Exit criteria:** `build_graph().compile().invoke({...})` runs through the placeholder nodes without error.

## Phase 1 — Lookup front end

**Goal:** Resolve a contract number against the contract-of-record, validate the match, and auto-fill the static SF-30 blocks. This is **deterministic** — no LLM (ADR-0006 §"Lookup is not an LLM step").

> **The lookup calls the SAM.gov API programmatically — never the AI.** The contract record is fetched by ordinary backend code in `lookup_node`, shaped to the official [SAM.gov Contract Awards API](https://open.gsa.gov/api/contract-awards/) (contract record + mod history, keyed by PIID) and [SAM.gov Entity Management API](https://open.gsa.gov/api/entity-api/) (contractor entity — UEI / CAGE / address → Block 8). The agent has **no SAM.gov tool** and never fetches documents — the fetch is plain code, the same way `/retrieve` is called, so a model can never widen the query, spoof a record, or cross the agency boundary.
>
> **Mock-backed in Phase 1 (PRD §4 non-goal).** The PRD marks real SAM.gov verification as mock-only, so Phase 1 ships a **mock SAM.gov client** behind the real API's request/response shape (Step 1.4) — seeded from the in-system `Award`/`Contract`/`Vendor` fixtures. Swapping the mock for the live API later is a client-internal change; `lookup_node` and the rest of the graph do not change.

### Step 1.1 — `lookup_node`

A node is just a function: it takes the state and returns the fields it wants to change. Keep the lookup itself in a small client so the node stays readable.

`app/workflow/nodes.py`
```python
from app.workflow import contract_lookup
from app.workflow.mock_sam_gov_client import MockSamGovClient

sam_gov = MockSamGovClient()   # Phase 1 mock; swap for the live SAM.gov client later


def lookup_node(state: WorkflowState) -> dict:
    """Resolve the contract number via the SAM.gov client (deterministic, no LLM)."""
    number = state["contract_number"]
    agency_id = state["change_request"]["agency_id"]

    record = contract_lookup.find_by_number(number, agency_id, sam_gov)

    # return only the keys we are updating; LangGraph merges them into the state
    return {"contract_record": record}
```

### Step 1.2 — `validate_lookup_node`

The contract number resolves to **exactly one** record or it does not. The failure modes are *not-found*, *multiple matches*, and *cross-agency* — each flags to the CO; nothing is fabricated.

```python
def validate_lookup_node(state: WorkflowState) -> dict:
    """Check the lookup result. On any problem, flag for CO review."""
    record = state["contract_record"]

    if record.get("match") == "found":
        return {"gate_status": "OK"}

    # not-found, ambiguous, or cross-agency -> surface to the CO, never guess
    return {"gate_status": "CONTRACT_NOT_FOUND_AWAITING_CO_REVIEW"}
```

### Step 1.3 — `populate_fields_node`

Auto-fill the static blocks (1, 2, 3, 6, 7, 8, 10A, 10B, 12) **from the record**, each carrying its source-of-record citation (system + record id + fetch time).

```python
def populate_fields_node(state: WorkflowState) -> dict:
    """Copy authoritative values into SF-30 blocks, each with a source citation."""
    record = state["contract_record"]
    citation = record["source_citation"]   # {"system": ..., "record_id": ..., "fetched_at": ...}

    fields = {}
    for block, value in record["static_fields"].items():
        fields[block] = {"value": value, "source_citation": citation}

    return {"populated_fields": fields}
```

### Step 1.4 — The SAM.gov lookup client (mock-backed, agency-scoped)

The lookup speaks the **SAM.gov API shape** behind one interface, so Phase 1's mock and the later live client are swappable with no change to `lookup_node`. Agency scope is enforced **here**, never trusted from the request (ADR-0005 §11 tenant isolation).

`app/workflow/contract_lookup.py`
```python
from app.workflow.sam_gov_client import SamGovClient


def find_by_number(contract_number: str, agency_id: str,
                   client: SamGovClient) -> dict:
    """Resolve the contract-of-record via the SAM.gov client (deterministic, no LLM).

    Agency scope is part of the query, so a CO can never resolve another
    agency's contract. The injected client is the mock in Phase 1 and the live
    SAM.gov adapter later; this function is identical either way.
    """
    matches = client.get_award(contract_number, agency_id)

    if len(matches) == 1:
        return _to_record(matches[0])
    if len(matches) == 0:
        return {"match": "not_found"}
    return {"match": "ambiguous"}
```

> The mock implements the official SAM.gov request/response shape — [Contract Awards API](https://open.gsa.gov/api/contract-awards/) + [Entity Management API](https://open.gsa.gov/api/entity-api/) — so the live swap is a client-internal change only.

**Exit criteria:** a known seed number returns one record with populated blocks + citations; an unknown number sets `CONTRACT_NOT_FOUND_AWAITING_CO_REVIEW`; another agency's number returns `not_found`; the agent has no path to call SAM.gov directly.

## Phase 2 — Classification + Block 14 grounded sub-pipeline

**Goal:** Classify the modification type (Block 13) and draft the rationale (Block 14). The Block 14 sub-pipeline is **ADR-0005 verbatim** — we call the existing `/retrieve` read path, we do not re-implement retrieval.

> Block 14 must route through the real `POST /retrieve` (`app/retrieval/router.py`), **not** the deliberately-broken `/draft-contract-modification` stub in `app/main.py` (ADR-0006 Integration Note 1).

### Step 2.1 — `classify_modification_node` (Block 13)

The agent reasons, then a deterministic retrieval feeds a Haiku classifier (FAR 43.103 A–E). **The LLM only classifies — it does not decide consent.** It proposes a Block 13 path (13A–13E), a `modType`, and a FAR basis, and it returns the *provenance* of that call (retrieved clause IDs, model + version, confidence) so the CO can verify it at the gate (Issue 4). Whether contractor consent is required is derived deterministically in Step 2.1b — never from the model's free text.

```python
from app.workflow import retrieve_client
from app import bedrock_client


def classify_modification_node(state: WorkflowState) -> dict:
    """Block 13: classify the modification type against FAR 43.103.

    The LLM proposes (block13_path, mod_type, far_basis, confidence). It does
    NOT decide consent — that is Step 2.1b (deterministic, server-side).
    Every input that drove the call is captured as provenance (Issue 4).
    """
    change = state["change_request"]

    # dense retrieve the governing FAR text; keep the clause IDs for provenance
    clauses = retrieve_client.retrieve(query=change["scope"], sf30_block="13",
                                       contract_id=state["contract_number"])
    answer = bedrock_client.invoke_model(
        prompt=f"Change: {change}\nFAR context: {clauses}\n"
               "Return JSON: block13_path (13A|13B|13C|13D|13E), mod_type "
               "(unilateral_change_order|unilateral_admin|bilateral_supplemental|unknown), "
               "far_basis (e.g. '43.103(a)'), confidence (0-1).",
        system="You classify post-award contract modifications under FAR 43.103. "
               "You classify only; you do not decide whether consent is required.",
    )
    proposed = bedrock_client.parse_json(answer["body"])

    classification = {
        "block13_path": proposed.get("block13_path"),
        "mod_type":     proposed.get("mod_type", "unknown"),
        "far_basis":    proposed.get("far_basis"),
        "confidence":   proposed.get("confidence", 0.0),
        # --- provenance surfaced at the CO gate (Issue 4) ---
        "retrieved_clause_ids": [c["id"] for c in clauses],
        "model":         answer["model"],
        "model_version": answer["model_version"],
    }
    return {"block13_classification": classification}
```

### Step 2.1b — `derive_consent_node` (deterministic, server-side)

Consent-required is a **legal rule on `modType`, not a model opinion** (Issue 1). A pure function maps the classified `modType` to FAR 43.103; an **unknown / unmapped** `modType` does **not** silently fall through to unilateral — it fails safe to consent-required *and* flags the package for CO review.

`app/workflow/far_rules.py`
```python
# FAR 43.103: modType -> contractor consent required?  Pure, deterministic, no LLM.
_CONSENT_RULES = {
    "bilateral_supplemental":  True,    # 43.103(a) — supplemental agreement, both sign
    "unilateral_change_order": False,   # 43.103(b)(1) — Changes clause, CO signs alone
    "unilateral_admin":        False,   # 43.103(b)(3) — administrative, CO signs alone
}


def consent_required_for(mod_type: str):
    """True/False per FAR 43.103, or None if the modType is unmapped.
    Caller treats None as 'CO must decide' — never assume unilateral."""
    return _CONSENT_RULES.get(mod_type)
```

`app/workflow/nodes.py`
```python
from app.workflow import far_rules


def derive_consent_node(state: WorkflowState) -> dict:
    """Map the classified modType -> consent rule (FAR 43.103). Unknown -> CO review."""
    mod_type = state["block13_classification"]["mod_type"]
    required = far_rules.consent_required_for(mod_type)   # no LLM in this path

    if required is None:                                  # unmapped / "unknown"
        return {"modification_bilateral": True,           # fail safe: needs consent
                "gate_status": "BLOCK13_UNCLASSIFIED_AWAITING_CO_REVIEW"}
    return {"modification_bilateral": required}           # True = bilateral
```

> **The agent never writes `contractorConsentRequired`.** The form-fill tools (Phase 3) write
> only `modType`; the contract-modification-service **re-derives** `contractorConsentRequired`
> from `modType` on the write path (same `consent_required_for` rule, unknown → consent-required)
> so the agent value can never widen or narrow the legal requirement. See ADR-0006
> §"Bilateral vs Unilateral".

### Step 2.2 — `retrieve_node` → `confidence_check_node`

`retrieve_node` calls the ADR-0005 endpoint. `confidence_check_node` then routes: pass (≥ 0.85) goes forward; fail surfaces to the CO. This is the first **conditional** edge.

```python
def retrieve_node(state: WorkflowState) -> dict:
    """Hybrid retrieval for the Block 14 rationale (ADR-0005 /retrieve)."""
    change = state["change_request"]
    result = retrieve_client.retrieve(query=change["scope"], sf30_block="14",
                                       contract_id=state["contract_number"])
    return {"retrieved_chunks": result["chunks"]}


def confidence_check_node(state: WorkflowState) -> dict:
    """Score the retrieval. Below 0.85 is a confidence failure (ADR-0005 §10)."""
    score = _mean_score(state["retrieved_chunks"])
    if score >= 0.85:
        return {"gate_status": "OK"}
    return {"gate_status": "RAG_FAILED_AWAITING_CO_REVIEW"}
```

### Step 2.3 — The routing function

`add_conditional_edges` needs a small function that reads the state and returns the **name of the next node**. It contains no logic beyond the branch.

```python
def route_after_confidence(state: WorkflowState) -> str:
    """Pass -> draft the rationale. Fail -> jump to the CO gate."""
    if state["gate_status"] == "OK":
        return "draft"
    return "co_gate"
```

Wire it in `build_graph()`:
```python
builder.add_node("derive_consent", nodes.derive_consent_node)
builder.add_node("retrieve", nodes.retrieve_node)
builder.add_node("confidence", nodes.confidence_check_node)

builder.add_edge("classify", "derive_consent")   # Step 2.1b — deterministic, no LLM
builder.add_edge("derive_consent", "retrieve")
builder.add_edge("retrieve", "confidence")
builder.add_conditional_edges("confidence", nodes.route_after_confidence,
                              {"draft": "draft", "co_gate": "co_gate"})
```

> Official `add_conditional_edges(node, routing_function, mapping)` pattern — see [add_conditional_edges reference](https://reference.langchain.com/python/langgraph/graph/state/StateGraph/add_conditional_edges).

### Step 2.4 — `draft_node` → `faithfulness_gate_node`

`draft_node` generates with Claude Haiku (Sonnet only on confidence-fail rerank — ADR-0004/0005). `faithfulness_gate_node` runs the RAGAS judge; below 0.85 routes to the CO, same shape as Step 2.2/2.3.

```python
def draft_node(state: WorkflowState) -> dict:
    """Block 14: Haiku drafts the rationale, grounded in the retrieved clauses."""
    answer = bedrock_client.invoke_model(
        prompt=f"Change: {state['change_request']}\n"
               f"Grounding clauses: {state['retrieved_chunks']}\n"
               f"Draft the SF-30 Block 14 modification rationale.",
        system="You draft FAR Part 43-compliant SF-30 rationale, grounded only "
               "in the provided clauses.",
    )
    return {"block_14_draft": answer["body"]}
```

**Exit criteria:** a good change request produces a drafted Block 14; a low-confidence or low-faithfulness run sets the matching `*_AWAITING_CO_REVIEW` status and routes to the gate instead of dead-ending.

## Phase 3 — Form-fill tool layer

**Goal:** Let the agent write a **draft** (`status = "DRAFT"`) into the existing `ContractModification` record through a small, allow-listed tool set. There is **no submit tool** — submission is a CO-only UI action (ADR-0006 §"Form-Fill Tool Layer").

The tools map to real fields on `ContractModification.java` (`contractNumber`, `modificationNumber`, `modType`, `farAuthority`, `fundingDelta`, `popStart`, `popEnd`, `contractorConsentRequired`, `description`, `sections`).

### Step 3.1 — The allow-listed write tools

Each tool writes one slice of the draft. They are plain functions the agent is allowed to call — nothing else can write.

`app/workflow/form_tools.py`
```python
from app.workflow import modification_client


def set_modification_basics(draft_id: str, contract_number: str,
                            modification_number: str, mod_type: str,
                            far_authority: str, effective_date: str,
                            agency_id: str) -> None:
    """SF-30 blocks 1, 2, 3, 10A, 13 -> the ContractModification draft."""
    modification_client.patch_draft(draft_id, {
        "contractNumber": contract_number,
        "modificationNumber": modification_number,
        "modType": mod_type,
        "farAuthority": far_authority,
        "effectiveDate": effective_date,
        "agencyId": agency_id,           # scoped on the write path too (Item 10)
    })


def set_block_14_rationale(draft_id: str, narrative: str,
                           price_cost_impact: str, funding_citation: str) -> None:
    """SF-30 block 14 -> description + sections on the draft."""
    modification_client.patch_draft(draft_id, {
        "description": narrative,
        "sections": {
            "changeNarrative": narrative,
            "priceCostImpact": price_cost_impact,
            "fundingCitation": funding_citation,
        },
    })
```

### Step 3.2 — `assemble_form_node`

The agent reasons, then calls the allow-listed tools above to populate the **draft** (never the live record).

```python
def assemble_form_node(state: WorkflowState) -> dict:
    """Write the looked-up blocks + drafted rationale into the DRAFT record."""
    draft_id = state["form_draft_id"]
    fields = state["populated_fields"]

    # Source mod_type and far_authority from block13_classification, not by
    # re-deriving from modification_bilateral (which would erase unilateral_change_order)
    # and not from populated_fields['13'] (which is never populated by the lookup).
    classification = state["block13_classification"]
    form_tools.set_modification_basics(
        draft_id=draft_id,
        contract_number=state["contract_number"],
        modification_number=fields["2"]["value"],
        mod_type=classification["mod_type"],
        far_authority=classification["far_basis"],
        effective_date=fields["3"]["value"],
        agency_id=state["change_request"]["agency_id"],
    )
    form_tools.set_block_14_rationale(
        draft_id=draft_id,
        narrative=state["block_14_draft"],
        price_cost_impact=state["change_request"].get("price_impact", ""),
        funding_citation=state["change_request"].get("funding_citation", ""),
    )
    return {"co_decision": "pending"}
```

**Exit criteria:** after this node the `ContractModification` draft has `status = "DRAFT"` and every block populated; no path can call a submit/publish action yet.

## Phase 4 — CO hard gate (pause / resume)

**Goal:** Pause the graph, show the CO the full package, and wait for **approve / deny**. The pause is a LangGraph **`interrupt`** backed by a **MongoDB checkpoint**, so a package survives a multi-day delay and a restart.

> New dependency: `langgraph-checkpoint-mongodb` (the `MongoDBSaver`). It reuses the Mongo instance already configured in `app/db.py`.

### Step 4.1 — `co_gate_node` using `interrupt()`

`interrupt()` pauses the graph and hands a payload to the UI. When the CO answers, `Command(resume=...)` sends the decision back and it becomes the return value of `interrupt()`.

```python
from langgraph.types import interrupt


def co_gate_node(state: WorkflowState) -> dict:
    """Hard CO gate. Pauses until the CO approves or denies."""
    decision = interrupt({
        "populated_fields": state["populated_fields"],   # blocks + source citations
        "block_14_draft": state["block_14_draft"],
        "gate_status": state["gate_status"],
        "bilateral": state["modification_bilateral"],
    })
    # execution resumes HERE when the CO answers via Command(resume=...)
    return {"co_decision": decision}   # "approved" or "denied"
```

> Official `interrupt()` + `Command(resume=...)` pattern — see [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) and the [interrupt reference](https://reference.langchain.com/python/langgraph/types/interrupt).

### Step 4.2 — Compile with the MongoDB checkpointer

`interrupt()` only works if the graph has a checkpointer (it persists the paused state). We use `MongoDBSaver`.

`app/workflow/runner.py`
```python
from langgraph.checkpoint.mongodb import MongoDBSaver

from app import config
from app.workflow.graph import build_graph


def run_until_gate(initial_state: dict, thread_id: str):
    """Start the workflow; it runs until the CO gate interrupt, then pauses."""
    with MongoDBSaver.from_conn_string(config.MONGO_URL, config.MONGO_DB) as saver:
        graph = build_graph().compile(checkpointer=saver)
        config_arg = {"configurable": {"thread_id": thread_id}}
        return graph.invoke(initial_state, config_arg)
```

```python
from langgraph.types import Command


def resume_after_decision(decision: str, thread_id: str):
    """Resume the paused workflow with the CO's approve/deny decision."""
    with MongoDBSaver.from_conn_string(config.MONGO_URL, config.MONGO_DB) as saver:
        graph = build_graph().compile(checkpointer=saver)
        config_arg = {"configurable": {"thread_id": thread_id}}
        return graph.invoke(Command(resume=decision), config_arg)
```

> Official `MongoDBSaver.from_conn_string(...)` + `compile(checkpointer=...)` pattern — see [langgraph-checkpoint-mongodb (PyPI)](https://pypi.org/project/langgraph-checkpoint-mongodb/) and [Memory / persistence](https://docs.langchain.com/oss/python/langgraph/add-memory).

### Step 4.3 — Route on the CO decision

```python
def route_after_co_gate(state: WorkflowState) -> str:
    """Deny -> supersede + restart. Approve -> consent check (Phase 5)."""
    if state["co_decision"] == "denied":
        return "supersede"
    return "consent_check"
```

**Exit criteria:** the graph stops cleanly at the gate; the same `thread_id` resumes the *same* package without re-running earlier nodes; deny routes to supersede, approve routes onward.

## Phase 5 — Bilateral consent + CO-only submit

**Goal:** A **bilateral** mod (FAR 43.103(a)) cannot submit until the contractor's Block 15 signature is **recorded**. A **unilateral** mod (FAR 43.103(b)) skips straight to submit. Consent is **never AI-generated** — it is a recorded human act (ADR-0006 §"Bilateral vs Unilateral").

### Step 5.1 — Route bilateral vs unilateral

```python
def route_after_approve(state: WorkflowState) -> str:
    """Bilateral -> contractor consent gate. Unilateral -> submit."""
    if state["modification_bilateral"]:
        return "consent_gate"
    return "submit"
```

### Step 5.2 — `consent_gate_node` (a second interrupt)

Same `interrupt()` mechanism as the CO gate — pause until the contractor's signature is recorded through the UI. Fail-closed: no recorded consent means the mod is not submitted.

```python
def consent_gate_node(state: WorkflowState) -> dict:
    """Bilateral only: pause until contractor consent (Block 15) is recorded."""
    consent = interrupt({"awaiting": "contractor_consent",
                         "draft_id": state["form_draft_id"]})

    if consent.get("signed") is True:
        return {"contractor_consent": "recorded"}
    return {"contractor_consent": "pending", "gate_status": "AWAITING_CONTRACTOR_CONSENT"}
```

### Step 5.3 — `submit_node` (CO-triggered, irreversible)

Submission flips `DRAFT → MODIFICATION_REQUEST`. The write path — **not** the agent — enforces CO role + recorded consent (ADR-0006 Integration Notes 2 & 3). The agent has no submit tool; this node only records the CO-triggered transition.

```python
def submit_node(state: WorkflowState) -> dict:
    """CO-triggered submit. The write path checks CO role + consent, fail-closed."""
    modification_client.publish(
        draft_id=state["form_draft_id"],
        consent_recorded=(state["contractor_consent"] == "recorded"),
    )   # service rejects if not CO, or bilateral without consent
    return {"gate_status": "SUBMITTED"}
```

> **Hard prerequisites on the write path before this can go live** (ADR-0006 §Consequences): CO-identity verification on `create`/`update`/`publish` (close the anonymous-default `X-User` header gap), one gateway-asserted identity convention across services (B1), and agency scoping on the write path (Item 10).

**Exit criteria:** a unilateral mod submits directly on approve; a bilateral mod blocks at submit until consent is recorded; the write path rejects a non-CO caller.

## Phase 6 — Audit log (cross-cutting)

**Goal:** Every node writes an append-only, correlation-id-threaded audit record. Audit for the **submit / decision / supersede** events must be **synchronous + transactional + fail-closed** — never the async-flush pattern that drops rows on crash (ADR-0006 Integration Note 3).

### Step 6.1 — One audit helper, called by every node

```python
from app.audit import logger as audit


def record_event(state: WorkflowState, event_type: str, details: dict) -> None:
    """Append one audit record. Raises on failure — no silent drops."""
    audit.write_audit_record({
        "correlation_id": state["form_draft_id"],
        "event_type": event_type,         # see the event list below
        "details": details,
    })
```

The event types (ADR-0006 §"Audit Log"):

| Event | Written by |
|---|---|
| `contract_lookup` | `lookup_node` (number, source system, record id, match result) |
| `static_fields_populated` | `populate_fields_node` |
| `form_field_written` | each form tool / `assemble_form_node` |
| `co_decision` | `co_gate_node` (approve/deny + CO identity, **synchronous**) |
| `contractor_consent_recorded` | `consent_gate_node` (bilateral only) |
| `package_superseded` | `supersede_node` (on deny) |
| `modification_submitted` | `submit_node` (**synchronous, transactional**) |
| `item_triaged` | `decision_router_node` (lane + disposition rationale, **every** item) |
| `auto_processed` | `auto_process_node` (auto lane — auditable like any gate, REQ-AGT-4) |

**Exit criteria:** every workflow run leaves a complete, ordered audit trail; killing the service mid-submit never loses the `modification_submitted` row.

## Phase 7 — The multi-agent triage flow (anomaly-detector → adjudicator → decision-router)

**Goal:** Triage **every** inbound item — modification requests **and** invoices — before any processing path runs (REQ-AGT-1). Three agents in sequence, then a **deterministic** router sorts each item into exactly one of three lanes (REQ-AGT-2). This is the **outer** graph; the SF-30 workflow (Phases 0–6) is the compiled **subgraph** it invokes on the HITL lane.

> **Detection is not disposition.** The detector only *flags*, the adjudicator only *substantiates flags against FAR*, and the router — a pure function — decides the lane. No agent self-authorizes; the lane is derived, never an LLM free-text opinion (mirrors the Step 2.1b consent rule).

### Step 7.0 — Extend the state for triage

The triage state **extends** `WorkflowState` so the SF-30 subgraph reads/writes the same channels (LangGraph requires parent + subgraph to share state keys).

`app/workflow/triage_state.py`
```python
from app.workflow.state import WorkflowState


class TriageState(WorkflowState):
    item_type: str             # "modification" | "invoice"
    idempotency_key: str       # money-path dedupe; a replay is a no-op (REQ-AGT-2)
    anomaly_flags: list         # [{code, detail, far_part, severity}] from the detector
    adjudications: list         # [{flag_code, verdict, far_cite, precedent_id}]
    lane: str                   # "auto_process" | "hitl_escalate" | "return_route"
    disposition_rationale: str  # why this lane — written to the audit trail (REQ-AGT-4)
```

### Step 7.1 — `anomaly_detector_node`

Flags typed anomalies. Mod-side: funding-ceiling breach, out-of-scope change. Invoice-side: unit-price variance, missing FAR 32.905 elements, potential FAR 31.205 unallowable cost. Deterministic numeric checks where possible; an LLM pass only for scope / unallowable-cost judgment. The detector **never** decides the lane.

```python
from app.workflow import anomaly_rules


def anomaly_detector_node(state: TriageState) -> dict:
    """Flag typed anomalies. Detection only — no disposition (REQ-AGT-1)."""
    item = (state["change_request"] if state["item_type"] == "modification"
            else state["invoice"])
    flags = anomaly_rules.scan(item, state["item_type"])   # [{code, detail, far_part, severity}]
    return {"anomaly_flags": flags}
```

### Step 7.2 — `adjudicator_node`

Tests each flag against the governing FAR clause + precedent through the **M2 retrieval path** (ADR-0005 `/retrieve`). A flag is **substantiated** only if a real clause supports it — otherwise dismissed (G2 "grounded or withheld").

```python
def adjudicator_node(state: TriageState) -> dict:
    """Test each flag against governing FAR + precedent (M2 retrieval, ADR-0005)."""
    results = []
    for flag in state["anomaly_flags"]:
        clauses = retrieve_client.retrieve(query=flag["detail"], far_part=flag["far_part"],
                                           contract_id=state["contract_number"])
        verdict = bedrock_client.invoke_model(
            prompt=f"Flag: {flag}\nFAR + precedent: {clauses}\n"
                   "Return JSON {verdict: substantiated|dismissed, far_cite, precedent_id}.",
            system="You adjudicate contract/invoice anomalies against FAR. A flag is "
                   "substantiated ONLY if a real, retrieved clause supports it.",
        )
        results.append(bedrock_client.parse_json(verdict["body"]))
    return {"adjudications": results}
```

### Step 7.3 — The auto-approval policy (explicit, bounded, default-deny)

REQ-AGT-6: the conditions under which the system may auto-act are **written down and testable**, not implicit. A pure function returns `True` only when **every** gate passes; any unmet or uncertain condition returns `False` → escalate. Reserved and irreversible actions are **hard exclusions** — model confidence cannot override them (REQ-AGT-2, "authority over accuracy").

`app/workflow/auto_approval_policy.py`
```python
# REQ-AGT-6: auto-approval is DEFAULT-DENY. Every condition must hold; any
# unmet/uncertain condition -> escalate. No confidence score overrides this.

RESERVED_ACTIONS = {
    "modification_execution",   # FAR 43.102 — only the CO executes a mod
    "payment_certification",    # irreversible money path
}


def may_auto_process(action: str, *, reversible: bool,
                     within_delegated_authority: bool, amount: float,
                     threshold: float, substantiated_flags: int) -> bool:
    """True only if ALL hold. Hard-excludes reserved / irreversible actions."""
    if action in RESERVED_ACTIONS:      return False   # never, regardless of confidence
    if not reversible:                  return False
    if not within_delegated_authority:  return False
    if amount > threshold:              return False
    if substantiated_flags > 0:         return False
    return True                                         # all gates clear -> auto lane
```

### Step 7.4 — `decision_router_node` (three lanes, `Command` routing)

The router reads the adjudications + policy and returns a `Command` that both **records** the lane (`update=`) and **routes** to it (`goto=`). The default branch is escalation; auto-process is the narrow, policy-proven exception.

```python
from langgraph.types import Command

from app.workflow import auto_approval_policy


def decision_router_node(state: TriageState) -> Command:
    """Sort the item into one lane. Default-deny: escalate unless auto is proven."""
    substantiated = [a for a in state["adjudications"] if a["verdict"] == "substantiated"]

    if _is_improper_invoice(state):                       # FAR 32.905 -> 7-day return
        return Command(goto="return_route",
                       update={"lane": "return_route",
                               "disposition_rationale": "improper invoice (FAR 32.905)"})

    if auto_approval_policy.may_auto_process(
            _action_of(state),
            reversible=_is_reversible(state),
            within_delegated_authority=_within_cor_authority(state),
            amount=_amount(state), threshold=_threshold(state),
            substantiated_flags=len(substantiated)):
        return Command(goto="auto_process",
                       update={"lane": "auto_process",
                               "disposition_rationale": "policy-clean: reversible, delegated, "
                                   "under threshold, no substantiated flags"})

    return Command(goto="hitl_escalate",                  # the default
                   update={"lane": "hitl_escalate",
                           "disposition_rationale": _escalation_reason(state, substantiated)})
```

> Official `Command(goto=..., update=...)` combined update-and-route pattern — see [Graph API overview](https://docs.langchain.com/oss/python/langgraph/graph-api).

### Step 7.5 — The three lane nodes + wiring the outer graph

- **`auto_process_node`** — idempotent mock execution + mandatory audit (REQ-AGT-2/4). Guards on `idempotency_key`: a replayed invoice is a no-op (no double-pay).
- **`hitl_escalate`** — for a modification, the **SF-30 workflow** (Phases 0–6) runs as a compiled subgraph and carries its own hard CO gate; an invoice payment pauses at a CO certification `interrupt()` (same primitive as Phase 4).
- **`return_route_node`** — return-to-vendor / request-more-info / route COR↔CO / hold; non-terminal.

```python
def auto_process_node(state: TriageState) -> dict:
    """Auto lane: idempotent mock execution + mandatory audit (REQ-AGT-2/4)."""
    if execution_log.already_processed(state["idempotency_key"]):
        return {"gate_status": "ALREADY_PROCESSED"}       # replay -> no double-pay
    mock_executor.process(state["form_draft_id"], state["idempotency_key"])
    record_event(state, "auto_processed",
                 {"lane": "auto_process", "rationale": state["disposition_rationale"]})
    return {"gate_status": "AUTO_PROCESSED"}
```

The existing SF-30 workflow compiles straight into the outer graph as the HITL node — no wrapper, because `TriageState` extends `WorkflowState` (shared state keys):

```python
from langgraph.graph import StateGraph, START

from app.workflow.graph import build_graph as build_sf30_workflow
from app.workflow.triage_state import TriageState
from app.workflow import nodes


def build_triage_graph() -> StateGraph:
    builder = StateGraph(TriageState)
    builder.add_node("anomaly_detector", nodes.anomaly_detector_node)
    builder.add_node("adjudicator", nodes.adjudicator_node)
    builder.add_node("decision_router", nodes.decision_router_node)
    builder.add_node("auto_process", nodes.auto_process_node)
    builder.add_node("return_route", nodes.return_route_node)

    # the SF-30 workflow (Phases 0-6) becomes the HITL processing subgraph
    builder.add_node("hitl_escalate", build_sf30_workflow().compile())

    builder.add_edge(START, "anomaly_detector")
    builder.add_edge("anomaly_detector", "adjudicator")
    builder.add_edge("adjudicator", "decision_router")
    # decision_router returns Command(goto=...) -> lane edges are dynamic, no static edges out
    return builder
```

> Official compiled-subgraph-as-node pattern (parent + subgraph share state keys) — see [Use subgraphs](https://docs.langchain.com/oss/python/langgraph/use-subgraphs). The router-then-specialized-agents shape follows the LangChain [multi-agent **router** pattern](https://docs.langchain.com/oss/python/langchain/multi-agent).

**Exit criteria:** every inbound item (mod or invoice, synthetic) exits in exactly one lane with a `disposition_rationale` (REQ-AGT-1); no reserved/irreversible action ever lands in `auto_process` regardless of model confidence (REQ-AGT-2); a replayed invoice is a no-op (REQ-AGT-2 idempotency); and the auto-approval conditions live in one testable function (REQ-AGT-6).

## Out of scope (per ADR-0006)

- Document upload / PyMuPDF / OCR — removed entirely; the lookup replaces it.
- Live SAM.gov calls — the SAM.gov API is fetched **programmatically** (deterministic `lookup_node` code, never an AI tool) but **mock-backed** in Phase 1 per PRD §4; the live adapter is a later client-internal swap.
- An agent `submit_modification` tool — submission is a CO-only UI action.
- AI-generated signatures or contractor consent — always a recorded human act.
